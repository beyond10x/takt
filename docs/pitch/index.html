what takt is

One binary that drives work through protocols

HarnessClaude Code today. Takes one admissible step at a time.
→
ValidatorsPrograms. Turn observations into evidence bound to the revision.
→
CanonProtocol engine. Decides which claims hold and if the outcome was earned.
→
GrantA merge happens only under a recorded grant.

The model never produces evidence.

Agents choose how to do the work. The protocol defines what must be true before the work counts.

thesis · selling points 1 and 2

Done is computed, and the rules are data

evidence, not claims

Done comes from validator records

Never from the model's text. What the harness says is a trace.

protocols as data

What must be true is a document

Versioned, reviewable, the same for every run. Not a prompt.

thesis · selling points 3 and 4

Merges need authority, and every case leaves a record

authority

A grant at the exact revision

No merge without a recorded grant. Judge surfaces need the owner's grant or a delegation on record.

replayable record

Every case is files in the repository

Every decision, step and evidence record. A later run resumes from it.

thesis · selling points 5 and 6

Bounded runs, any harness

bounded autonomy

Budgets and named stops

Iterations, hours and tokens. Each stop has a name and an exit code an orchestrator can drive.

harness-neutral

The harness is an adapter

Claude Code now, others behind the same seam. The same protocol judges any model.

thesis · selling point 7

Self-improvement under a pinned judge

  1. takt improves takt in measured turns.
  2. A fix counts only when a predicate held before and fails after, on the same scenario.
  3. A release is promoted only if no scenario regresses.

Designed in design:recursive-self-improvement. One turn has been accepted so far, recorded by hand. The scorecard, promotion and the pinned judge are not built yet.

Reading the numbers

  • Against Claude Code with the operator's full configuration, takt used 4.7× fewer tokens at 1.9× lower cost. Nearly all of that gap is the isolation, not the protocol: the isolated arm runs Claude Code with takt's harness isolation (restricted mode, no MCP servers, no hooks) plus a shell and the file tools. takt's own harness has the file tools only.
  • One toy scenario, a 31-line change to a CLI, n=3 per row. Every arm passed 3/3, so the held-out check does not tell them apart. First results, not a benchmark.
  • Token totals include cache reads, billed at about 1/20 of input. Cost is the API list price the harness reports: notional. Compare cost beside tokens, not tokens alone.
  • Codex is another vendor. Its model is read from its configuration, not from the run, and it reports no cost.
  • The resumes at 97623a6 and 447423c are a repository.inspect step followed by NoProgress (story:no-inspect-for-stateless-harness). takt at 0a776d2 needed an https-origin workaround for a bug in its trial fetch; without it, 0/3 runs got past the fetch.
  • Every figure is in docs/metrics/scenario-runs.jsonl, 29 runs.

Six deviations, as the run record labels them:

  1. Hand records. A recorder program wrote the evidence; no takt run drove the case.
  2. The order of e4. The scorecard was recorded before the merge could be.
  3. Producer. The planner ran e2–e4, not the reviewer the design names.
  4. Tokens from a shim. A claude shim recorded them, not the run's events.
  5. Promotion tied by sha256. The binary embeds no revision.
  6. Recorder outside the repository. Built against wave 10 code at 93bd7c3, which made the merge grant recordable (story:grant-binds-to-action-subject, not yet in main).

The design's promotion default (median tokens at most baseline + 10%) would fail on these figures. Two of the three candidate runs hit the known NoProgress stop; putting the +24% down to that is an inference. Whether the rule applies at n=3 is open. beyond the numbers

takt's case is not efficiency: it is what the free runs did not give

Evidence records bound to a revision
A merge only under a grant; refused without one
A replayable case record a later run resumes from
A stop with a named reason and an exit code
Self-improvement under a pinned judge

The price on this toy scenario: about 1.7× the cost and 2× the wall time of the isolated free agent. n=3, one scenario.

Counterpoint

takt's own independent review found that a model step could make the test validator report pass by editing the build or test configuration. It is filed with severity high as story:step-cannot-forge-its-validators and is not built. A protocol-level review catching it is part of the thesis. The fix has not landed.

the current plan

Roadmap

  1. Scenario 1 accepted unattended: one invocation plus one grant, daily for a week (story:story-done-end-to-end, and the waste stories). This is the entry to phase R1.
  2. The self-improvement chain: story:scorecard-reader → story:promotion → story:judge-guard → story:self-improvement-protocol. Then a turn is driven by takt's validators instead of hand records. The scorecard reader is in wave 10, not yet in main.
  3. A forge through the user's gh login for repositories outside the organization (story:plain-gh-forge).
  4. Then continuous runs: planning as a unit, a tree of cases, one deterministic dispatcher.
