what takt is

One binary that drives work through protocols

HarnessClaude Code today. Takes one admissible step at a time.
→
ValidatorsPrograms. Turn observations into evidence bound to the revision.
→
CanonProtocol engine. Decides which claims hold and if the outcome was earned.
→
GrantA merge happens only under a recorded grant.

The model never produces evidence.

Agents choose how to do the work. The protocol defines what must be true before the work counts.

thesis · selling points 1 and 2

Done is computed, and the rules are data

evidence, not claims

Done comes from validator records

Never from the model's text. What the harness says is a trace.

protocols as data

What must be true is a document

Versioned, reviewable, the same for every run. Not a prompt.

thesis · selling points 3 and 4

Merges need authority, and every case leaves a record

authority

A grant at the exact revision

No merge without a recorded grant. Judge surfaces need the owner's grant or a delegation on record.

replayable record

Every case is files in the repository

Every decision, step and evidence record. A later run resumes from it.

thesis · selling points 5 and 6

Bounded runs, any harness

bounded autonomy

Budgets and named stops

Iterations, hours and tokens. Each stop has a name and an exit code an orchestrator can drive.

harness-neutral

The harness is an adapter

Claude Code now, others behind the same seam. The same protocol judges any model.

thesis · selling point 7

Self-improvement under a pinned judge

  1. takt improves takt in measured turns.
  2. A fix counts only when a predicate held before and fails after, on the same scenario.
  3. A release is promoted only if no scenario regresses.

Designed in design:recursive-self-improvement. One turn has been accepted so far, recorded by hand. A second is in progress: its candidate is measured and not merged. The promotion rule, decided 2026-10-18: five candidate runs per scenario; worse on tokens when the candidate's median is above the baseline's maximum; outcomes compared with a margin of one case. The scorecard reader is built (wave 10); promotion and the pinned judge are not.

What the measurements say

The isolated free agent was cheaper and faster. takt at 0a776d2 cost about 1.7× as much ($0.25 against $0.14), used 1.3× the tokens and took 2.1× the wall time (133 s against 64 s). The later revisions were not cheaper. Round 3 points the same way: takt used 1.5× the tokens of the isolated arm and took 2.7× its wall time (138,580 against 93,003; 142 s against 53 s, n=3 each). With the model pinned, takt at a0b8576 took 122,361 tokens and 127 s (n=5). The isolated arm was not run again; against its 92,772 tokens and 55.5 s that is 1.3× the tokens and 2.3× the time.

  • In round 1, against Claude Code with the operator's full configuration, takt used 4.7× fewer tokens at 1.9× lower cost. Nearly all of that gap is the isolation, not the protocol: the isolated arm runs Claude Code with takt's harness isolation (restricted mode, no MCP servers, no hooks) plus a shell and the file tools. takt's own harness has the file tools only.
  • One toy scenario, a 31-line change to a CLI, n=2 to 6 per row. Every run with a result passed the held-out check (45 of 45), so it does not tell the arms apart. First results, not a benchmark.

Reading the numbers

  • Round 3's models. takt passed no --model, and its model changed under it: T-11 and T-13 ran every call on claude-fable-5-1, T-12 its first call on fable and then opus. The cause is unknown; account rotation is an inference. So takt's round 3 cost ($0.47–0.85) can't be compared with rounds 1 and 2. The isolated arm ran on opus; Claude Code with the full configuration ran on fable. From round 4 the runner pins --model claude-opus-5-5 for every Claude arm.
  • Claude Code with the full configuration was slower and dearer in round 3 than in round 1 (112 s and $1.38 against 65 s and $0.48). Nobody has checked why. Its model and the operator's plugin set both changed between the rounds.
  • Token totals include cache reads, billed at about 1/20 of input. Cost is the API list price the harness reports: notional. Compare cost beside tokens, not tokens alone.
  • Codex is another vendor. Its model is read from its configuration, not from the run, and it reports no cost.
  • The resumes at 97623a6, 447423c and 98719c3 (T-27) are a repository.inspect step followed by NoProgress (story:no-inspect-for-stateless-harness). takt at 0a776d2 needed an https-origin workaround for a bug in its trial fetch; without it, 0/3 runs got past the fetch.
  • T-10 is a runner race, not a takt result: a free-arm run had just pushed the trial branch takt was about to create, so takt refused before its first step. It is recorded and not counted.
  • Every figure is in docs/metrics/scenario-runs.jsonl, 57 runs.

Six deviations, as the run record labels them:

  1. Hand records. A recorder program wrote the evidence; no takt run drove the case.
  2. The order of e4. The scorecard was recorded before the merge could be.
  3. Producer. The planner ran e2–e4, not the reviewer the design names.
  4. Tokens from a shim. A claude shim recorded them, not the run's events.
  5. Promotion tied by sha256. The binary embedded no revision then; it does since wave 11 (story:binary-embeds-revision).
  6. Recorder outside the repository. Built against wave 10 code at 93bd7c3, which made the merge grant recordable (story:grant-binds-to-action-subject, not in main then; merged with wave 10 at 333d369).

The promotion default the design held then (median tokens at most baseline + 10%) would fail on these figures. Two of the three candidate runs hit the known NoProgress stop; putting the +24% down to that is an inference. The rule decided later that day (n=5; worse when the candidate's median tokens are above the baseline's maximum) would not pass it either: 151,626 is above its baseline's maximum, 136,180 (T-1..3), and above the maximum of the n=5 baseline at a0b8576, 138,160 (T-14..18). beyond the numbers

takt's case is not efficiency: it is what the free runs did not give

Evidence records bound to a revision
A merge only under a grant; refused without one
A replayable case record a later run resumes from
A stop with a named reason and an exit code
Self-improvement under a pinned judge (designed; the judge is not built)

The price on this toy scenario: about 1.7× the cost and 2× the wall time of the isolated free agent, n=3 on one model. Round 3 kept the gap in tokens and time; its cost is not comparable. At a0b8576, n=5 with the model pinned: about 1.8× the cost and 2.3× the wall time ($0.25 against $0.14; 127 s against 55.5 s).

Counterpoint

takt's own independent review found that a model step could make the test validator report pass by editing the build or test configuration. It was filed with severity high as story:step-cannot-forge-its-validators. The fix merged with wave 10 at 333d369, after two adversary passes and four rounds of correction (docs/waves/wave-10.md). A protocol-level review catching it is part of the thesis. No scenario run tries to forge evidence yet, so no record measures whether the fix holds.

the current plan

Roadmap

  1. Scenario 1 accepted unattended: one invocation plus one grant, daily for a week (story:story-done-end-to-end, and the waste stories). This is the entry to phase R1.
  2. The self-improvement chain: story:scorecard-reader → story:promotion → story:judge-guard → story:self-improvement-protocol. Then a turn is driven by takt's validators instead of hand records. The scorecard reader merged with wave 10 at 333d369. Since wave 11, merged at 8378cb2, the binary embeds the revision it was built from, which promotion builds on.
  3. A forge through the user's gh login for repositories outside the organization (story:plain-gh-forge).
  4. Then continuous runs: planning as a unit, a tree of cases, one deterministic dispatcher.
