# Story: takt-tui-crate

## Outcome

A dedicated crate, `crates/takt-tui`, holds the terminal frontend, generated by `ess generate ui --target tui --model ess` from `ess/ui/takt.ui.yaml` and never edited by hand; `takt tui --repo <path>` starts `takt serve` on a free 127.0.0.1 port and the `takt-tui` binary bound to it, and stops the server when the app quits.

## Context

epic:terminal-frontend, step 4. Depends on story:tui-ui-document and story:takt-serve-read-only.

Facts the developer builds on (beyond10x/ess 0.60.0):
- the generated crate is a binary crate, a clap `src/main.rs` with `--base-url` and `--screen-once` calling `ess_ui_tui::run_embedded` (`crates/ui/ess-ui-tui/src/generate.rs:8-9,226-249`), so `takt-cli` cannot link it: `takt tui` spawns the `takt-tui` binary;
- it depends on `ess-ui-tui` fetched by the Git tag of the ESS release that generated it (`ess generate ui --help`), so takt's `Cargo.toml` and `Cargo.lock` gain a Git dependency on beyond10x/ess at that tag; both are on takt's judge surface;
- the generated app polls `live:` sections at their `refresh:` (`app.rs:193-195`).

Where `takt tui` finds `takt-tui`: beside the running `takt` executable, else on `PATH`; absent, it exits 1 naming the install command. `cargo install --path crates/takt-tui` (or the workspace's install command) is documented in AGENTS.md by the developer and in the site by the doc-writer.

The regeneration check runs the ESS release CI installs (`ESS_VERSION`, `.github/workflows/check.yml:57-71`); a different local `ess` refuses the check by name rather than producing a diff.

No `ESS_UI_AUTHORIZATION` is set: the epic has no write route.

## Expected before

On takt at main, holds; after the change, fails:

- `ls crates/takt-tui/Cargo.toml` exits non-zero.

## Scope

- `crates/takt-tui/**` (generated) (inferred)
- `crates/takt-cli/src/main.rs`: the `tui` command (inferred)
- `Cargo.toml` (workspace member), `Cargo.lock`, `Taskfile.yml` (the regeneration check), `AGENTS.md` (install line) (inferred)

## Acceptance

`takt tui --repo <scratch repository with recorded cases> --screen-once 120x40` prints one frame of the case list naming a recorded case and exits 0; `task check` fails when `crates/takt-tui` differs from a fresh `ess generate ui --target tui --model ess --path ess/ui/takt.ui.yaml` and when the local `ess` is not the release CI installs; with `takt-tui` absent, `takt tui` exits 1 naming the install command; and after the app quits, no `takt serve` process started by it is running (checked by its pid).
