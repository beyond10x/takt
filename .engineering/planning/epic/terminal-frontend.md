# Epic: terminal-frontend

## Outcome

A person watches and steers takt from a terminal: the cases of a repository, each case's frontier (claims, admissible actions, outcomes), its run events as they arrive, the pending approvals, the scorecard and the journey of each run, and grants an approval from the same screen. The frontend is specified before it is built: an `ess-ui/1` document checked against takt's ESS model, its data served by a read-only local `takt serve` that `ess verify conform` holds to the model, and the terminal app generated from the document into its own crate.

## Context

Owner request of 2026-10-18: "use /ess:specifying with ess UI spec to create a dedicated crate for a tui frontend in rust". ESS 0.60.0 has a renderer-neutral UI format, `ess-ui/1` (`ess ui load | check | docs | run | test`), with a terminal renderer: `ess ui run --tui` runs a document against fixtures or, with `--model`, against the HTTP surface the specification's components serve; `ess ui test` runs `ess-ui-test/1` tests headless against the terminal renderer; `ess generate ui --target tui` generates a crate that embeds the document and binds it to a served surface at `--base-url` (beyond10x/ess `crates/ui/ess-ui-tui/src/lib.rs:242`, `run_embedded`). The worked example is beyond10x/ess `examples/partner-portal/ui.yaml`.

takt serves no HTTP today; its state is files (`.engineering/cases/<id>/`: case.yaml, decisions/, evidence/, events.jsonl, authority.yaml). Decided by the planner role on 2026-10-18: the frontend reads through a read-only `takt serve` bound to localhost, implementing the views the model declares, so the same views are checked by `ess verify conform`; the one write, granting an approval, comes last and goes through `takt::case::grant` with a person's identity, never an agent's.

## Stories, in order (spec first)

1. story:tui-read-model: declare the views (cases, case detail, run events, approvals pending, scorecard, journey) and their HTTP surface in `ess/domains/takt.yaml`.
2. story:tui-ui-document: the `ess-ui/1` document `ess/ui/takt.ui.yaml`, fixtures read from real cases, and `ess-ui-test/1` tests that pass headless.
3. story:takt-serve-read-only: `takt serve --repo <path>`, localhost only, read only, serving the views; `ess verify conform` against it.
4. story:takt-tui-crate: `crates/takt-tui` generated by `ess generate ui --target tui` from the document, `takt tui` starts `takt serve` and the app.
5. story:tui-approve-action: the approve command in the model, the document and `takt serve`, writing a grant under a person's identity.

## Acceptance

On a repository with recorded cases, `takt tui` opens on the case list, a case shows its claims, actions and outcomes from its latest decision and its run events, a case at `ApprovalRequired` can be approved by a person from the screen, and every view the app reads passes `ess verify conform` against `takt serve`.
