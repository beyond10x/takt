takt

One open-source binary that drives a repository's work through engineering protocols. Point it at a repository: it takes an intent or the next ready story, opens a case on a protocol, and lets a harness such as Claude Code take one admissible step at a time.

Nothing counts until a validator has turned an observation into evidence. Canon decides which claims hold and whether an outcome was earned; the model never does.

Agents choose how to do the work. The protocol defines what must be true before the work counts.

The problem: a free-running harness grades its own work

A coding agent running free decides when it is done and says so in text. Nothing ties that claim to the commit that gets merged, and the same agent usually holds the rights to push and merge.

How a run works

  1. Protocol. A Canon document declares the claims, the actions, the evidence that establishes each claim, and the actions that wait for a grant, for example software.change/1 or story.delivery/1.
  2. Case. Each unit of work (an intent or a story from the planning store) opens a case on a protocol, held as files in the repository.
  3. One step at a time. Canon evaluates the case and names the admissible actions; the harness performs one of them in a worktree and reports. What it says is a trace, not evidence.
  4. Validators make evidence. A program turns an observation (a test run's exit status, a gate result, a pull request's CI, a merged pull request) into an evidence record bound to the revision it observed.
  5. Grant before merge. A merge through the repository's bot route happens only under a recorded grant (takt approve). The run stops with exit code 4 and waits; the next run resumes the case.
  6. A named stop. Every run ends on a budget (iterations, hours, tokens), a named stop or completion, each with its own exit code, so an orchestrator can drive it.

The honest result. On scenario 1 the isolated free agent was cheaper and faster: takt cost about 1.7× as much ($0.25 against $0.14), used 1.3× the tokens and took 2.1× the wall time (133 s against 64 s), and the later revisions were not cheaper. Round 3 pointed the same way: 1.5× the tokens and 2.7× the wall time of the isolated arm (138,580 against 93,003; 142 s against 53 s, n = 3 each). With the model pinned, takt at a0b8576 took 122,361 tokens and 127 s (n = 5); the isolated arm was not run again, and against its 92,772 and 55.5 s that is 1.3× the tokens and 2.3× the time. Against Claude Code with its full configuration takt used 4.7× fewer tokens at 1.9× lower cost, and nearly all of that gap is the isolation, not the protocol. The hypothesis "cheaper per accepted unit" is not supported on this scenario.

  • One toy scenario: a 31-line change to a CLI. Every counted run passed (45 of 45 with a result), so the held-out check does not tell the arms apart.
  • Round 3's models. takt passed no --model, and its model changed under it: two runs used claude-fable-5-1 for every call, the third for its first call only. The cause is unknown; account rotation is an inference. takt's round 3 cost ($0.47–0.85) can't be compared with rounds 1 and 2. The isolated arm ran on opus, Claude Code with the full configuration on fable. From round 4 every Claude arm is pinned to claude-opus-5-5.
  • Claude Code with the full configuration was slower and dearer in round 3 (112 s and $1.38 against 65 s and $0.48). Nobody has checked why; its model and the plugin set both changed between the rounds.
  • One run at 834205f, T-27, stopped on NoProgress after a repository.inspect step and needed one resume. No run since round 3 changed model: every call was claude-opus-5-5.
  • One more takt run, T-10, refused before its first step because a concurrent free-arm run had taken its trial branch. It is a runner race, recorded and not counted.
  • Token totals include cache reads, billed at about 1/20 of input. Cost is the API list price the harness reports: notional. Codex is another vendor: it reports no cost, and its model was read from its configuration, not from the run.
  • takt at 0a776d2 needed an https-origin workaround for a bug in its trial fetch; without it, 0/3 runs got past the fetch.
  • Source: docs/metrics/scenario-runs.jsonl in the takt repository (not yet on GitHub), 57 runs, one record each, naming the raw usage record it was read from. A figure the source does not state is null.

Six deviations from the protocol as designed, as the run record labels them: hand records (a recorder program wrote the evidence; no takt run drove the case); the scorecard recorded before the merge could be; the planner, not the reviewer, as producer of the checks; tokens from a shim, not from events; promotion tied by sha256, since the binary embedded no revision (it has since wave 11); and a recorder outside the repository, built against wave 10 code that was not in main then. The design's promotion default (median tokens at most baseline + 10%) would fail on these figures. Two of the three candidate runs hit a known NoProgress stop, and blaming the +24% on that is an inference.

Why takt anyway

takt's case is not efficiency. It is what the free runs did not give. The price on this toy scenario is about 1.7× the cost and 2× the wall time of the isolated free agent, measured on one model. Round 3 and the 15 takt runs after it kept the gap in tokens and time.

  • Evidence, not claims. Done is computed from validator records bound to a revision, never from the model's text.
  • Authority. A merge happens only under a grant recorded for the exact revision; without one it is refused.
  • The record. Every case is files in the repository: each decision, step and evidence record. A later run resumes from it, and a reviewer can replay it.
  • Named stops. Budgets for iterations, hours and tokens, and a stop with a reason and an exit code.
  • Self-improvement under a pinned judge. takt improves takt in measured turns. A fix counts only when a predicate held before and fails after, on the same scenario, and a release is promoted only if no scenario regresses. The first turn was recorded by hand; the pinned judge is not built.

Still to be shown, in this order: less supervision (scenario 1 accepted unattended), then improvement under the judge (a turn driven by takt's validators, not by hand). Later: that accepted means verified, which scenario 1 cannot tell, since every arm passed; and safety under scenarios that try to forge evidence. A review found that a model step could make the test validator pass by editing build or test configuration; that fix (story:step-cannot-forge-its-validators) landed in wave 10.

Roadmap

  1. Scenario 1 accepted unattended: one invocation plus one grant, daily for a week. The waste above is part of that work.
  2. The self-improvement chain: scorecard reader, then promotion, then the judge guard, then validators for self.improvement/1, so that a turn is driven by takt rather than by hand. The scorecard reader landed in wave 10. Since wave 11 the binary records the revision it was built from, which promotion builds on.
  3. A forge through the user's gh login for repositories outside the organization.
  4. Then continuous runs: planning as a unit, a tree of cases, one deterministic dispatcher.

Getting started

Build

cargo install --locked --path crates/takt-cli
takt --version

Needs a harness (Claude Code, claude on the PATH, or --harness none for validators only); for story runs, aep and its planning store in the repository; for pull requests, an origin on github.com with b10x-gates and gh on the PATH.

Run

takt run --repo <path> --intent "make the failing test pass" --iterations 1
takt run --repo <path> --hours 1

The first opens a case on software.change/1. The second resumes the open case of a story, or takes the next ready story and opens its case on story.delivery/1.

Approve

takt approve --repo <path> <case> repository.merge --by <who>

A run that waits for the merge exits 4. The grant is recorded in the case; the next takt run merges under it.

Scenario run

takt scenario run --repo <path> <id> --hours 1

Replays a declared scenario on a fresh trial/<n> branch cut from its seed commit, so its pull request targets that branch. takt run --help lists every default and the exit codes; the README has the details.
