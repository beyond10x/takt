takt

One open-source binary that drives a repository's work through engineering protocols. Point it at a repository: it takes an intent or the next ready story, opens a case on a protocol, and lets a harness such as Claude Code take one admissible step at a time.

Nothing counts until a validator has turned an observation into evidence. Canon decides which claims hold and whether an outcome was earned; the model never does.

Agents choose how to do the work. The protocol defines what must be true before the work counts.

The problem: a free-running harness grades its own work

A coding agent running free decides when it is done and says so in text. Nothing ties that claim to the commit that gets merged, and the same agent usually holds the rights to push and merge.

How a run works

  1. Protocol. A Canon document declares the claims, the actions, the evidence that establishes each claim, and the actions that wait for a grant, for example software.change/1 or story.delivery/1.
  2. Case. Each unit of work (an intent or a story from the planning store) opens a case on a protocol, held as files in the repository.
  3. One step at a time. Canon evaluates the case and names the admissible actions; the harness performs one of them in a worktree and reports. What it says is a trace, not evidence.
  4. Validators make evidence. A program turns an observation (a test run's exit status, a gate result, a pull request's CI, a merged pull request) into an evidence record bound to the revision it observed.
  5. Grant before merge. A merge through the repository's bot route happens only under a recorded grant (takt approve). The run stops with exit code 4 and waits; the next run resumes the case.
  6. A named stop. Every run ends on a budget (iterations, hours, tokens), a named stop or completion, each with its own exit code, so an orchestrator can drive it.

The honest result. On scenario 1 the isolated free agent was cheaper and faster: takt cost about 1.7× as much ($0.25 against $0.14), used 1.3× the tokens and took 2.1× the wall time (133 s against 64 s). Against the free agents with their full configuration takt used 4.7× fewer tokens at 1.9× lower cost, and nearly all of that gap is the isolation, not the protocol. The hypothesis "cheaper per accepted unit" is not supported on this scenario.

  • One scenario: a 31-line change to a toy CLI. All arms passed 3/3, so the held-out check does not tell them apart.
  • Token totals include cache reads, billed at about 1/20 of input. Cost is the API list price the harness reports: notional. Codex reports no cost; its model was read from its configuration, not from the run.
  • takt at 0a776d2 needed an https-origin workaround for a bug in its trial fetch; without it, 0/3 runs got past the fetch.
  • Two known overheads are filed: a model step spent only on asking for the merge approval (about 30k tokens per run), and CI running twice because the pull request opens before the tests are written.
  • Source: docs/metrics/scenario-runs.jsonl in the takt repository at d634ace, one record per run, each naming the raw usage record it was read from. A figure the source does not state is null.

Why takt anyway

takt's case is not efficiency. It is what the free runs did not give. The price on this toy scenario is about 1.7× the cost and 2× the wall time of the isolated free agent.

  • Evidence, not claims. Done is computed from validator records bound to a revision, never from the model's text.
  • Authority. A merge happens only under a grant recorded for the exact revision; without one it is refused.
  • The record. Every case is files in the repository: each decision, step and evidence record. A later run resumes from it, and a reviewer can replay it.
  • Named stops. Budgets for iterations, hours and tokens, and a stop with a reason and an exit code.
  • Self-improvement under a pinned judge. takt improves takt in measured turns. A fix counts only when a predicate held before and fails after, on the same scenario, and a release is promoted only if no scenario regresses.

What is still to be shown: that accepted means verified (escaped defects per accepted unit), less supervision (touches from outside the run), and safety (no forged evidence or merge without a grant, under scenarios that try).

Roadmap

  1. Scenario 1 accepted unattended (one invocation plus one grant), daily for a week.
  2. The first takt release promoted by its own scorecard.
  3. A gh-login forge for repositories outside the organization.
  4. Then continuous runs: planning as a unit, a tree of cases, one deterministic dispatcher.

Getting started

Build

cargo install --locked --path crates/takt-cli
takt --version

Needs a harness (Claude Code, claude on the PATH, or --harness none for validators only); for story runs, aep and its planning store in the repository; for pull requests, an origin on github.com with b10x-gates and gh on the PATH.

Run

takt run --repo <path> --intent "make the failing test pass" --iterations 1
takt run --repo <path> --hours 1

The first opens a case on software.change/1. The second resumes the open case of a story, or takes the next ready story and opens its case on story.delivery/1.

Approve

takt approve --repo <path> <case> repository.merge --by <who>

A run that waits for the merge exits 4. The grant is recorded in the case; the next takt run merges under it.

Scenario run

takt scenario run --repo <path> <id> --hours 1

Replays a declared scenario on a fresh trial/<n> branch cut from its seed commit, so its pull request targets that branch. takt run --help lists every default and the exit codes; the README has the details.
